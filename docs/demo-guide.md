## 1. 展示目标

课堂展示应证明三件事：

1. 系统功能设计有逻辑，覆盖完整赛事生命周期。
2. 系统能够现场运行，数据处理正确。
3. 项目具有技术难点和设计亮点，尤其是单淘汰树和权限控制。

## 3. 推荐演示流程

### 3.1 普通用户视角

1. 登录 `player_mike`。
2. 打开赛事大厅。
3. 搜索或筛选赛事。
4. 进入赛事详情。
5. 展示赛事编号、时间、地点、状态、报名进度。
6. 打开消息通知和个人运动档案。

说明重点：

- 赛事大厅是统一入口。
- 用户可按编号、分类、状态检索。
- 报名、通知、积分和档案形成闭环。

### 3.2 主办方视角

1. 登录 `org_zs`。
2. 打开赛事工作台。
3. 展示赛事列表和报名管理。
4. 展示批量生成参赛者和随机积分。
5. 打开抽签与淘汰树。
6. 展示种子、轮空、晋级和撤销。

说明重点：

- 主办方不需要线下表格管理名单。
- 多人数据可快速构造，便于测试和演示。
- 淘汰树是项目技术难点。

### 3.3 管理员视角

1. 登录 `test_admin`。
2. 打开审核与风控。
3. 展示赛事审核、驳回原因和审核记录。
4. 展示用户管理、封禁/删除/批量生成。

说明重点：

- 管理员负责平台治理。
- 前端路由和后端接口都做权限校验。
- 公开赛事不能绕过审核直接上线。

## 4. 重点讲解句

### 项目定位

> 乐赛不是单一报名表，而是将赛事发布、报名审核、赛程生成、结果归档和消息通知整合起来的赛事组织平台。

### 权限模型

> 系统按 RBAC 思路区分参赛者、主办方和管理员，前端负责入口控制，后端负责真正的接口权限校验。

### 状态流转

> 赛事状态、报名状态和赛程节点状态都由后端接口统一修改，避免前端随意改状态导致数据不一致。

### 淘汰树

> 淘汰树先根据参赛人数计算最近的 2 的幂，再计算轮空位。种子选手只有在存在轮空位时才优先保送，节点支持晋级、退赛和撤销。

## 6. 常见提问回答

### 为什么不是只做报名功能？

因为赛事组织不是单点操作，还包括审核、名单、赛程、结果、积分和通知。只做报名无法体现完整业务闭环。

### 树图为什么是技术难点？

因为实际人数不一定是 2 的幂，还要处理种子轮空、节点晋级、退赛、撤销和持久化，既有算法问题，也有状态一致性问题。

### 为什么通知不是 WebSocket？

课程项目使用事件刷新和短轮询已经可以满足课堂演示和基本即时反馈。商业级实时聊天可以进一步升级为 WebSocket。
