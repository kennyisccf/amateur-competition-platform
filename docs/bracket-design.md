# 单淘汰树与种子逻辑设计说明

## 1. 设计目标

乐赛的赛程树用于支撑单淘汰赛事。它不是静态图片，而是一个可推进、可回滚、可持久化的比赛状态结构。

设计目标：

- 支持任意参赛人数，而不只支持 2、4、8、16。
- 支持种子选手保护。
- 支持首轮轮空。
- 支持晋级、退赛、比分录入、结果撤销。
- 支持只有 1 名参赛者的边界场景。
- 前端能够在人数较多时保持树图可读。

## 2. 核心概念

| 概念 | 说明 |
| --- | --- |
| `n` | 审核通过的实际参赛人数 |
| `bracket_size` | 大于等于 `n` 的最小 2 的幂 |
| `bye_slots` | 轮空位数量，等于 `bracket_size - n` |
| seed | 种子选手，通常按积分或配置顺序获得保护 |
| node | 一场比赛节点，保存选手、比分、胜者和状态 |
| `bracket_state` | 持久化存储在 competition 表中的赛程 JSON 状态 |

## 3. 生成流程

```text
读取审核通过参赛者
  -> 计算 bracket_size
  -> 计算 bye_slots
  -> 选择种子选手
  -> 种子优先进入 bye
  -> 普通选手随机填充剩余位置
  -> 生成第一轮节点
  -> 生成后续轮次空节点
  -> 保存 bracket_state
```

## 4. bracket size 与轮空位

人数不是 2 的幂时，需要补齐到标准赛程结构。

示例：

| 实际人数 `n` | `bracket_size` | `bye_slots` |
| --- | --- | --- |
| 1 | 特殊边界 | 0 |
| 6 | 8 | 2 |
| 13 | 16 | 3 |
| 32 | 32 | 0 |

计算方式：

```text
bracket_size = nextPow2(n)
bye_slots = bracket_size - n
```

## 5. 种子逻辑

当前最终规则：

- 种子不等于无条件保送。
- 只有存在 `bye_slots` 时，种子才优先首轮保送。
- 如果轮空位数量少于种子数量，优先保护排序更高的种子。
- 如果没有轮空位，种子进入正常对阵，但尽量分散，避免过早相遇。

这样可以避免一个常见错误：种子已经被首轮保送，却又被放入第一轮与普通选手比赛。

## 6. 节点状态

赛程节点可以理解为一个小型状态机。

| 状态 | 含义 |
| --- | --- |
| draft | 待准备 |
| active | 待比赛或进行中 |
| completed | 已完成 |
| bye | 轮空自动晋级 |
| forfeited | 一方退赛 |
| reverted | 结果已撤销 |

实际页面中会根据节点数据展示“待定、比分、胜者、冠军”等文字。

## 7. 晋级与回滚

### 7.1 晋级

当前节点产生胜者后：

1. 写入当前节点胜者。
2. 将胜者推进到下一轮对应节点。
3. 更新当前节点状态。
4. 如果是决赛节点，写入冠军和排名结果。

### 7.2 撤销

撤销不是简单清空当前节点。它需要：

1. 清除当前节点胜者和比分。
2. 清除由该胜者推进到后续节点的位置。
3. 防止旧胜者残留在半决赛、决赛或冠军节点。
4. 重新计算可操作状态。

## 8. 只有 1 人参赛的边界

当审核通过参赛者只有 1 人时，系统不再生成无意义对阵，而是按特殊边界处理：

- 页面不应报错。
- 可展示唯一参赛者。
- 可根据业务状态显示“待决出/自动冠军”等结果。

## 9. 前端布局

前端根据后端 `bracket_state` 渲染：

- 按轮次分列。
- 每轮节点纵向排列。
- 使用连线表示上一轮到下一轮的晋级关系。
- 容器宽度和高度根据轮次数与节点数计算。
- 人数多时拉开行距，减少节点重叠。

## 10. 课堂答辩说明

可以这样概括：

> 淘汰树的核心是先把实际人数补齐到最近的 2 的幂，再计算轮空位。种子选手只有在存在轮空位时才优先保送，避免种子同时出现在首轮对阵中。每个比赛节点都是一个状态机，支持晋级、退赛、比分录入和撤销，最终把冠军、排名和积分写回个人档案。
